# AI 协作与迭代记录

本文记录作品从需求、失败结果、人工判断到代码验证的完整链路。Git 历史保留了每轮可运行版本，便于评委复查，不以一次性“大提交”替代过程证据。

## 迭代一：从分散工具改为双语精读工作台

### 用户目标

> “左侧放原文内容，右侧就是对应的翻译内容，并且在原文中可以使用鼠标来选择高亮语句，并且在译文中也可修改。”

### AI 初始方案

将原文预览、章节导读和需要复制粘贴的翻译入口合并为同一页面；按 PDF 页码管理原文、译文和高亮位置，并提供同步滚动。

### 人工判断与修正

用户明确指出“功能多”并不等于“阅读顺畅”，要求删除复制段落这一步。最终设计把双语对照设为核心工作区，而不是继续增加独立工具页。

### 工程结果

- 左右双栏、按页翻译、自动翻译开关；
- 原文 Range 选择和四色高亮；
- 译文 Markdown 预览与可编辑模式；
- 数据写入 IndexedDB，刷新后保留。

对应提交：`e7c11af`。

## 迭代二：修复 PDF 文本“逐行碎裂”问题

### 用户反馈

> “通过 AI 提取文字后要进行合理的排版，美化一点，且图片也要识别到。”

### 暴露的问题

PDF.js 返回的是带坐标的字符项，不是天然段落。直接拼接会把作者、单位和正文拆成大量短行；仅靠 CSS 无法修复错误的文本结构。图片也不属于文本抽取结果。

### AI 方案与人工约束

- 先按 y 坐标聚合同一行，再根据间距、缩进、字号和标点合并段落；
- 将文本分类为标题、章节、正文、列表、图注、元数据和公式；
- “图片识别”不夸大为视觉理解，而是增加原始页面渲染，完整保留图片、表格和公式供核对；
- 保存布局版本号，使旧文献只需重解析一次。

### 工程结果

对应提交：`cca4327`、`0583c7b`。验证包括 TypeScript、ESLint、生产构建和真实论文首页截图。

## 迭代三：从“能排版”到“像学术阅读器”

### 用户反馈

> “这种文字排版还是太难看了，给我修改。”

### 失败原因分析

第一版虽然消除了逐字符碎裂，但把作者和单位误判为普通标题，正文宽度、行高和层级也没有形成学术文档的节奏。译文仍像一整段聊天输出。

### 改进决策

- 为论文首页单独识别题名、作者、单位、摘要和关键词；
- 限制正文行宽，统一段落间距和两端对齐；
- 自动把译文规范化为 Markdown 标题、作者信息、单位列表、摘要和关键词；
- 保留编辑入口，避免自动排版覆盖用户校订。

### 工程结果

对应提交：`db78c8a`。这轮反馈说明：生成式界面必须把用户视觉判断纳入迭代证据，而不是只展示代码完成度。

## 迭代四：面向评审的可信性闭环

### 评估发现

自测发现三个高风险点：中文问题在英文论文中容易漏检；模型可能生成未被检索到的页码；未配置 Key 时评委无法快速体验。

### 改进

- 本地中英学术词表 + 模型查询改写；
- BM25 长度归一化与词项稀有度评分；
- 把本轮召回页写入提示词白名单，并在输出后再次校验；
- 回答下展示真实检索片段，点击跳回原文；
- 增加原创合成演示论文，离线预置双语内容和证据问答。

### 验证标准

`typecheck`、`eslint`、`build` 全部通过；无 Key 时能完成演示；非法页码被标记为待核验；证据卡可跳转到对应页。

## 人机分工原则

- 人负责目标、取舍、视觉判断、真实性边界和最终验收。
- AI 负责方案展开、代码实现、错误定位、重复验证和材料整理。
- 任何合成数据必须显式标注，不能把演示结果描述为真实研究结论。
- 每个关键改动都通过可运行代码和 Git 提交固化，避免只保留聊天截图。
